3. Resumen Ejecutivo 
Este proyecto consiste en el diseño de un sistema bancario basado en microservicios, 
desplegado en un cluster local de Kubernetes, aplicando principios de DevOps y SRE desde 
su concepción. 
 
El sistema estará compuesto por 5 microservicios independientes que se comunicarán de 
forma asincrónica mediante un broker de mensajería. Se definirán métricas de confiabilidad 
(SLI), objetivos (SLO) y acuerdos (SLA), además de documentación completa de arquitectura. 
 
4. Enunciado del Proyecto 
 
4.1 Descripción del problema o necesidad a resolver 
 
Las instituciones financieras requieren sistemas altamente disponibles, escalables y 
resilientes capaces de procesar transacciones de manera confiable en entornos distribuidos. 
Los sistemas monolíticos tradicionales presentan limitaciones en: 
● Escalabilidad horizontal  
● Tolerancia a fallos  
● Independencia de despliegue  
● Evolución tecnológica  
Ante este contexto, se plantea la necesidad de diseñar un sistema bancario basado en una 
arquitectura de microservicios que adopte principios de DevOps y Site Reliability 
Engineering (SRE), priorizando la confiabilidad, el desacoplamiento y la comunicación 
asíncrona entre componentes. 
 
Definición de Microservicios 
Visión general del dominio 
El sistema bancario estará compuesto por los siguientes microservicios: 
1. Customer Service  
2. Account Service  
3. Transaction Service

Restricciones arquitectónicas 
● No se permite comunicación síncrona (HTTP u otros protocolos similares) entre 
microservicios  
● Toda interacción entre servicios debe realizarse mediante mecanismos asíncronos  
● El API Gateway debe actuar únicamente como punto de entrada al sistema  
● Cada microservicio debe ser autónomo y desacoplado. 
● Cada microservicio debe de poseer su base de datos. 
● No se permite antipatrones de microservicios. Tales como microservicios conectados 
a múltiples bases de datos. La forma de comunicación debe ser estrictamente entre 
microservicios, ningún microservicio puede consultar bases de datos que no sean la 
correspondiente. Caer en el incumplimiento de esta restricción será penalizable con 
el 50% de la nota obtenida.

6. Metodología 
A continuación se presenta una metodología estructurada que el estudiante debe seguir 
para abordar el desarrollo del proyecto, priorizando el diseño arquitectónico, la 
comunicación asíncrona y la confiabilidad del sistema. 
Pasos a seguir: 
 
1. Paso 1: Definición del dominio 
Definir los 5 microservicios, sus responsabilidades, datos y eventos. Asegurar que 
cada servicio sea autónomo y no comparta base de datos con otros. 
 
2. Paso 2: Diseño de microservicios  
Analizar el dominio bancario y definir las entidades principales (cliente, cuenta, 
transacción, pago). Identificar límites de contexto (bounded contexts) para dividir 
correctamente los microservicios. 
 
3. Paso 3: Definición del modelo de comunicación   
Seleccionar el mecanismo de mensajería (Kafka, RabbitMQ, NATS o gRPC 
asíncrono) y definir el patrón de comunicación: 
● Event-driven  
● Request/Reply  
● Pub/Sub  
Justificar la elección en términos de desacoplamiento y resiliencia. 
 
4. Paso 4: Diseño de eventos y contratos    
Definir los eventos que se intercambiarán entre servicios: 
● Nombre del evento  
● Estructura del payload  
● Uso de correlationId  
Establecer convenciones para topics o subjects. 
 
5. Paso 5: Diseño de la arquitectura (Diagramas)  
Elaborar los diagramas obligatorios: 
● C4 (Contexto, Contenedores, Componentes)  
● UML (Secuencia, Despliegue, Casos de uso)  
Asegurar consistencia entre todos los diagramas. 
 
 
6. Paso 6: Definición del flujo de negocio (Saga) 
Diseñar el flujo de transferencia bancaria utilizando el patrón Saga: 
● Flujo exitoso  
● Manejo de fallos  
● Eventos de compensación 
 
7. Paso 7: Definición de métricas SRE    
Definir: 
● SLI (indicadores)

Software Avanzado 
Proyecto - vigente para el Segundo Semestre 2026  
 
 
● SLO (objetivos)  
● SLA (acuerdos)  
Relacionarlos con el comportamiento del sistema. 
 
8. Paso 8: Implementación de microservicios   
Desarrollar los microservicios utilizando el lenguaje y framework seleccionado. 
Implementar: 
● Publicación de eventos  
● Consumo de eventos  
● Lógica de negocio 
 
9. Paso 9: Implementación del API Gateway    
Desarrollar el API Gateway como punto de entrada del sistema. Este debe integrarse 
con el mecanismo de mensajería para iniciar flujos de negocio de manera asíncrona. 
 
10. Paso 10: Contenerización del sistema  
Crear Dockerfiles para cada microservicio y el gateway. Validar ejecución local de 
cada componente. 
 
11. Paso 11: Despliegue en Kubernetes    
Configurar el cluster local (minikube, kind o k3d) y desplegar: 
● Microservicios  
● Gateway  
● Broker (si aplica)  
Las bases de datos deben estar fuera del cluster. 
 
12. Paso 12: Pruebas de integración    
Validar el flujo completo del sistema: 
● Transferencias exitosas  
● Manejo de errores  
● Consumo correcto de eventos 
13. Paso 13: Documentación final 
Integrar toda la documentación: 
● Diagramas  
● Justificación tecnológica  
● SLI/SLO/SLA  
● Casos de uso 
 
 
Recomendaciones 
 
● Diseñar antes de programar; evitar comenzar directamente con código 
● Mantener separación estricta entre microservicios 
● No utilizar comunicación síncrona entre servicios 
● Definir claramente los eventos antes de implementar 
● Implementar idempotencia en consumidores de eventos 
● Utilizar identificadores de correlación (correlationId) en todos los flujos
