Bank USAC — release "{{ .Release.Name }}" installed into namespace "{{ .Release.Namespace }}".

External mode: {{ .Values.external.mode }}
{{- if eq .Values.external.mode "dockerNetwork" }}
  Pods reach the databases, RabbitMQ and MinIO through selectorless Services
  backed by Endpoints pointing at their real IPs on the shared Docker
  network `bank-usac-local`. If any pod never becomes Ready, the most likely
  cause is a stale IP in those Endpoints — Docker reassigns them whenever a
  container is recreated. Regenerate with:

    infra/k8s/kind/scripts/discover-external-ips.sh

  and re-run `helm upgrade` with the file it writes.
{{- else }}
  Pods reach the databases, RabbitMQ and MinIO through ExternalName Services
  pointing at host.docker.internal, on the Compose-published ports (5433-5437
  for the five PostgreSQL instances, 5673 for RabbitMQ, 9002 for MinIO).
  This is the fallback path from ADR-007 — confirm it is intentional; the
  dockerNetwork mode is preferred when the kind cluster shares a Docker
  network with the Compose stack.
{{- end }}

0. If any pod shows `ImagePullBackOff` or `ErrImageNeverPull` instead of
   Running, this is not a dependency problem — it never got as far as
   starting. Nothing on this node satisfies that image name. Run

     pnpm images:build -- --kind bank-usac    # the kind cluster, not the release

   which builds every component and loads both the short-commit tag and `dev`
   onto the node, then re-run `pnpm k8s:install` so the release names the
   commit it is running rather than whatever was built last.

1. Check that every workload is Ready before touching anything else — a pod
   stuck at Running/0-1 Ready is reachable but its dependencies are not:

     kubectl get pods -n {{ .Release.Namespace }} -w

   Per-component detail, including which of database/broker/queues is the
   one still failing:

     kubectl exec -n {{ .Release.Namespace }} deploy/{{ include "bank-usac.componentFullname" (dict "root" $ "component" .Values.services.customer.component) }} \
       -- wget -qO- http://127.0.0.1:{{ .Values.services.customer.port }}/ready

2. Reach the system the way the assignment does — kubectl port-forward, the
   documented access path for this single-node local cluster (there is no
   Ingress controller and no LoadBalancer here):

     kubectl port-forward -n {{ .Release.Namespace }} \
       svc/{{ include "bank-usac.componentFullname" (dict "root" $ "component" .Values.gateway.component) }} 3000:{{ .Values.gateway.port }}

     kubectl port-forward -n {{ .Release.Namespace }} \
       svc/{{ include "bank-usac.componentFullname" (dict "root" $ "component" .Values.web.component) }} 3010:{{ .Values.web.port }}

   Run both in separate terminals (or backgrounded), then open
   http://localhost:3010. This only works if `web.apiBaseUrl` /
   `gateway.corsAllowedOrigins` were left at their defaults
   (http://localhost:3000 / http://localhost:3010) or were both overridden
   to match the ports actually forwarded above — the browser resolves the
   API base URL, not the cluster, so a mismatch here is a CORS error, not a
   crash.

3. The five domain services publish no port outside the cluster (by
   design — the Gateway is the system's only entry point) and so are not
   reachable with port-forward's usual "curl it from your machine" pattern
   for anything but debugging via `kubectl exec`/`kubectl port-forward`
   directly against their own Service if needed.

4. A pod that is Running but never Ready is not necessarily broken — see
   docs/operations/CONTAINERS.md, "Liveness is not readiness": readiness
   answers 503 while a dependency is unreachable, and that is retried
   automatically. Give it the readiness probe's periodSeconds before
   assuming something is actually wrong, then read its /ready body (step 1)
   for which dependency it is still waiting on.

5. Capture what this release actually looks like — pods, services, nodes, the
   out-of-cluster containers and every component's /ready body:

     pnpm k8s:evidence

   It only reads, and it writes into specs/008-audit-remediation/evidence/.

The full procedure, prerequisites and troubleshooting live in
docs/operations/DEPLOYMENT.md; the decision behind this shape is ADR-007.
