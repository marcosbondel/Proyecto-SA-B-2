# Implementation Plan: Infraestructura local de desarrollo (T-06)

**Branch**: `feature/T-06` | **Date**: 2026-08-20 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/006-local-dev-infra/spec.md`

## Summary

This feature provisions the local development stack that every blocked ticket depends on: five isolated PostgreSQL 18.4 databases (one per service), a RabbitMQ 4.3.4-management broker with the topology defined in T-05, and a MinIO object-store buffer for identity-document photos. All components run outside the Kubernetes cluster through a single `docker compose` file under `infra/docker/`, attached to a fixed Docker network that kind nodes can join. The deliverables include reproducible startup, credential isolation, executable failure evidence, and the security-policy updates that close the two T-06 blockers in `docs/SECURITY.md`.

## Technical Context

**Language/Version**: Docker Compose v2 syntax; shell scripts for executable evidence; TypeScript for the broker integration test that closes TD-014.

**Primary Dependencies**:
- `postgres:18.4` — five independent service databases.
- `rabbitmq:4.3.4-management` — single-node broker with management plugin.
- `minio/minio:RELEASE.2024-11-07T00-52-20Z` — S3-compatible object store (release chosen in research.md).
- `mc` (MinIO Client) in an init container to create the bucket and set the 24-hour retention policy.

**Storage**: Five named Docker volumes (`pgdata-*`) plus `rabbitmq-data` and `minio-data`. No bind mounts for application data.

**Testing**: Executable shell evidence scripts plus one TypeScript integration test against `@bank/messaging` for broker publish/consume and reconnection behavior.

**Target Platform**: Local Docker on macOS/Linux/Windows (Docker Desktop), with connectivity to a local kind cluster.

**Project Type**: Local infrastructure / development tooling.

**Performance Goals**: Stack healthy in under 5 minutes from a clean clone on a developer machine; broker and database health checks pass within 60 seconds of container start.

**Constraints**:
- No database, broker, or object-store manifests inside `infra/k8s/` (constitution III).
- No real credentials committed; all secrets live in `.env` loaded from `.env.example`.
- Each PostgreSQL user may only access its own database (constitution II).
- The broker topology must be byte-for-byte idempotent with `docs/events/topology.md`.

**Scale/Scope**: Single-node local development; not production clustering. One Compose project per clone.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-checked after Phase 1 design.*

| Principle | Verdict | Justification |
|---|---|---|
| I. Exactly five microservices | **PASS** | No microservice is created, merged, or reassigned. The stack only provisions external infrastructure for the existing five services. |
| II. One database per service with no cross-access | **PASS** | Five independent PostgreSQL services, each with a dedicated database, user, and volume. Credential isolation is enforced by PostgreSQL `pg_hba` and explicit grants, validated by an executable test (5 own / 20 cross rejected). |
| III. Databases outside the cluster | **PASS** | All persistence and messaging infrastructure runs in Docker Compose, not in `infra/k8s/`. The deliverable explicitly removes any database/broker/object-store manifests from the Kubernetes directory. |
| IV. Asynchronous service communication only | **PASS** | No service-to-service HTTP is introduced. The broker is provisioned; its topologies match the event-driven contracts from T-05. |
| V. Gateway-only entry with no business logic | **N/A** | No Gateway code is changed. The object store is reachable only as a transfer buffer; business logic remains in Customer Service. |
| VI. Saga for distributed operations | **N/A** | No Saga logic is implemented here; the broker topology supports the Saga events already defined in T-05. |
| VII. Local Kubernetes deployment | **PASS** | The Compose stack is attached to a fixed Docker network (`bank-usac-local`) that kind nodes join; selectorless Services in T-22 will consume it. `host.docker.internal` is documented as fallback. |
| VIII. SRE from design | **PASS** | Health checks, bounded retry evidence, `correlationId` visibility in the broker test, and DLQ headers are all part of the deliverable. |

**Post-design re-check**: No change. The design remains conforming.
